name: update-setup
description: Update this Claude Code setup (the rules, hooks, skills and project folders it installed) to the newest released version, keeping the user's own files and settings. Use when the user types /update-setup, says "update the setup", "install the update", "is there a newer version", asks "what's new" or "что нового", or says yes after the update-check reminder.

# Update the setup

The update is one script; your part is to run it, deal with the few things it can't do alone, and say what changed. It only writes the setup's own files. Skills, hooks, settings and notes the user added themselves are never touched, one of the setup's files that the user changed stays as they have it, and every file it replaces is kept, as it was, in `~/.claude/setup-logs/<YYYY-MM-DD>-install-backup/` under its path from the home folder (never next to the file). Copies an older version left next to a file as `<name>.before-install-<date>` move there on the first update.

A release that asks the person nothing installs itself: the update-check hook runs `update.mjs --quiet` (the whole installer unseen, panel builds included) or `--files-only` in the background, and `~/.claude/update-check.json` `auto` holds the last one (version, time, ok or its error, `extFailed`, `panels`). Only a release with a new question, a step only a chat can do, or a higher Claude Code minimum waits for this skill. When a background install failed or a panel could not be updated, a normal run of this skill tries again; after a failed panel it runs the installer again even when it says `Already on the newest version`. Its `kept` lists the files the user changed, which it left as theirs: if they ask for the new version of them, run the script with `--replace <name>` for each (or `--replace-all`), as in step 3.

**Asked what's new** ("what's new", "что нового") with no update wanted: read `version` and `repo` (the folder the setup was installed from) in `~/.claude/setup-state.json` and give the tour of step 9 from `~/.claude/setup-source/v<version>/docs/whats-new.md`, else from `<repo>/docs/whats-new.md` (an install from a clone), with the path you read; run nothing else. When neither is there, say so in one line, give the public page `<REPO_URL>/blob/main/docs/whats-new.md` (`REPO_URL` is set near the top of `update.mjs`) and offer `/update-setup`.

1. **Run it:** `node ~/.claude/skills/update-setup/update.mjs` (allow up to 10 minutes: a changed extension is rebuilt). It also updates Claude Code itself and prints the version of the Claude Code that Nimbalyst ships; pass on a line starting `Nimbalyst runs its own Claude Code` or `Nimbalyst's Claude Code: now yours` as it is (new Nimbalyst chats then run the person's own Claude Code). Stop, giving the message as it is, when it says Claude Code is too old or could not update itself while running, or prints `Update stopped:` (nothing was changed). If it prints `Already on the newest version`, say so in one line, make the offers of steps 2 and 2b when there are any, do step 10, then stop.
2. **Rules.** Pass the `rules:` line on in one sentence (the setup's rules are always this version's; rules the person added are moved to `~/.claude/rules/my-rules.md`, which loads in every chat too, and the line names its undo). For each `notes: brought <folder>/CLAUDE.md up to this version` line, say in one sentence that the project folder's notes are this version's again and the rules the person had added there were moved to the `my-rules.md` the line names, in that folder's `.claude/rules`. Then run `node ~/.claude/skills/update-setup/own-rules.mjs --status --homes`; only if a file says `changed since last tidy`, run the same script with `--offered` (so the next prompt's reminder doesn't offer it twice) and make one offer on the question card (`AskUserQuestion`; in Nimbalyst `mcp__nimbalyst__AskUserQuestion`), yes (recommended) / not now, with the lines of all its files and about bytes ÷ 4 tokens: `Your own rules: <n> lines, about <t> tokens in every chat. Tidy them? Lines the setup already covers or does better go to a vault you can restore from; your own preferences stay. One command undoes it.` On yes: read `~/.claude/skills/update-setup/tidy.md` and follow it. On not now: `node ~/.claude/skills/update-setup/own-rules.mjs --skip --homes`. No question per rule. If the person says they don't need a setup rule ("I don't need the rule about design work"), run `node ~/.claude/skills/update-setup/update.mjs --leave-out "<the rule's bold opening, else its first six words>"`, with no form; `--put-back "<same>"` brings it back.
2b. **Disk, files, backup and auto mode.** Pass each `disk:` line on as it is (`disk: freed …` is the setup cleaning its own leftovers). The person decides on their own leftovers, on the file reorganize and, once each, on the backup and on auto mode. These go on one question card (`AskUserQuestion`; in Nimbalyst `mcp__nimbalyst__AskUserQuestion`), with one question for each of these lines:
   - each line starting `offer:` (from disk-tidy);
   - a `files-offer:` line;
   - a `project-pass: level …` line;
   - a `Backup: not asked` line;
   - an `Auto mode: not asked` line, only in Nimbalyst, where `mcp__nimbalyst-host__workspace_set_trust` is found. In a terminal, skip it and run nothing, so the next update in Nimbalyst asks.

   No such lines, no card. Each question in plain words, with the numbers its line gives:
   - own leftovers: `Your own leftovers: about <size> (<what>). Look through them now? About 2 minutes; nothing goes without your yes per item.` Options `Look through them now (recommended)` / `Not now`;
   - the chat archive (an `offer: Chats older than …` line): the line's own words, `Yes (recommended)` / `Not now`;
   - files: `<n> files in <m> project folders could be renamed or moved to the setup's layout, about <x> minutes. Every change is shown first and one command undoes it.` Options `Reorganize now (recommended)` / `Not now`;
   - backup (a `Backup: not asked` line; no option is marked recommended, not everybody needs it): `Back up your Claude setup to the cloud, encrypted? Your settings, rules, skills, memory and any project folders you pick are copied to your own Backblaze B2 storage on the schedule you pick (daily, weekly or only when you ask); it is free up to 10 GB, then about $7 per TB a month. They are locked on this computer with a password only you keep, so Backblaze or anyone with the storage key sees only scrambled data. Setup takes about 10 minutes: you make a Backblaze account and keep one password. The backup has been tested against a folder on a computer, not yet against a live Backblaze account or a live schedule.` Options `Yes, set it up` / `No (we won't ask again; /backup sets it up any time)`;
   - auto mode (an `Auto mode: not asked` line): `Let Claude work without asking before each step? A second model checks every command and file change first: safe ones go ahead, risky ones are stopped and you are asked.` Options `Yes, turn on auto mode (recommended)`, because the setup's notes and guards are built for it and it removes most permission pop-ups, / `No, keep asking me (we won't ask again)`;
   - project folders (a `project-pass: level <old> → <new>, <n> folders behind` line): `<n> project folders you worked in lately were set up before this version of Stratus. When you next work in one, offer to bring it up to date, so sessions there get the current rules, systems map and file layout (about 15 minutes each, every change shown first)?` Options `Yes, when I open each (recommended)` / `Now, starting with <newest folder>` (the first `behind` line of `node ~/.claude/skills/update-project/pass.mjs --list`) / `No, don't offer`.

   What to do on each answer:
   - Leftovers, chat archive and files: on yes, after the rest of the update, run `/disk-tidy` (leftovers, chat archive) or `/file-upkeep` (files). On not now: for files run `node ~/.claude/skills/file-upkeep/file-check.mjs --skip --homes` (the next update then asks only about new findings); then one line, `Any time: /disk-tidy` or `Any time: /file-upkeep`.
   - Backup: yes: `node ~/.claude/skills/update-setup/update.mjs --backup yes` (it puts the yes on record, so the next update doesn't ask again), then, after the rest of the update, run `/backup`; no: `node ~/.claude/skills/update-setup/update.mjs --backup no` (it only puts the answer on record), then `Any time: /backup`.
   - Any other `Backup:` line (setup not finished, last run failed, last good run days ago) gets no card: pass it on in the reply as it is.
   - Auto mode, yes: `node ~/.claude/skills/update-setup/update.mjs --auto-mode yes`, then `mcp__nimbalyst-host__workspace_set_trust` with `trusted: true`, `mode: "bypass-all"`, `allowAllUsesClassifier: true` for the project this chat runs in and for `claude-settings` and `quick-tasks` in the projects folder (`projects` in `~/.claude/setup-state.json`) where they exist. Each result's after-values must read `bypass-all` and `true`, else report the failure. Then one line: it is set per project, and any other project gets it in Settings > Project > Agent Permissions, "Agent-verified".
   - Auto mode, no: `node ~/.claude/skills/update-setup/update.mjs --auto-mode no`, then `Any time: Settings > Project > Agent Permissions, Agent-verified`.
   - Project folders: yes needs nothing run (the offer comes in each folder); now: after the rest of the update, `/update-project` on that folder by its path, with no window opened; no: `node ~/.claude/skills/update-project/pass.mjs --skip-all`, then `Any time: /update-project in a project folder`.
3. **Files they changed.** Only if the output has the line `Kept as yours`: the files listed under it are the setup's, but the user changed them (or had their own under that name), so they were not replaced and are now behind this version. Show the list and ask once: take this version's copy of all of them, of some (which ones), or keep theirs. A copy of theirs is kept in `~/.claude/setup-logs/<YYYY-MM-DD>-install-backup/` either way. All: `node ~/.claude/skills/update-setup/update.mjs --replace-all`. Some: the same command with `--replace <name>` for each, the name as the list has it.
4. **Extensions.** The installer builds a changed Nimbalyst extension into a side folder and puts it in only while Nimbalyst is closed: `extension installed: <name>` means it is in place, `extension waiting: <name> (...)` that it is built and waits for Nimbalyst to close (step 10), `extension unchanged` that nothing was needed. For a line `extension failed: <name> (...)`, give the reason; the installed one stays and the next update builds it again.
5. **Plugins.** `plugin installed:` and `plugin already there:` need nothing. For a line `plugin failed`, `skill failed` or `plugins not installed`, give the reason it names; the next update tries again. If `~/.claude/skills/phone-bot/pc/setup.mjs` exists, run it with `status`; when it says `running: yes`, the phone app's PC program still runs the old code: run it with `remove`, then `start-logon`, then `start` to start it again. The keys stay, so the phone needs no new pairing. A phone that has the app open meanwhile shows that it is connecting, then comes back by itself within a few seconds of the program's start, on the screen it was on; it says the PC is off only if the program stays away 20 seconds or more. A `phone voice:` line says the phone's voice setup started in the background (about 480 MB, nothing to do); pass it on in one sentence.
6. **Language.** The language question is asked only once. If the output has the line `Language: not chosen`, ask in a form with one singleSelect, English or Русский. Then run `node ~/.claude/skills/update-setup/update.mjs --language <english|russian>`, and call the Nimbalyst tool `mcp__nimbalyst-host__ai_set_preferred_language` with `ru` for Русский or an empty string for English (when that tool is available). `/update-setup russian` or `/update-setup english` changes the language at any time, with no question: run the same command with that language. After a change, say that Nimbalyst needs one restart for the buttons and that new chats answer in that language, and write the reply in the chosen language.
7. **Model.** Only if the output has a line starting `MODEL CHANGED`: an install of this setup at version 1.0.74 or earlier (its numbering before the year-based versions) that had `"model": "sonnet"` and no effort setting was moved to Opus at medium effort. Do not ask; say it in the reply, with the line's own words, and give the undo the line prints. `/update-setup --keep-model` runs `node ~/.claude/skills/update-setup/update.mjs --keep-model`, which puts `sonnet` back and keeps it on every later update. A line `model: sonnet is back` says that was done. A line `MODEL CHANGED in quick-tasks` says that folder moved from Sonnet to Opus once; its undo is `/update-setup --keep-home-model`, which leaves the global model alone.
7b. **Ink look.** Only if the output has a line starting `theme: set now:` (Nimbalyst is open, so the installer could not write it). Call `mcp__nimbalyst-host__appearance_set_theme` with `com.local.inktheme:ink-cobalt`. Only if that call succeeds, run `node ~/.claude/skills/update-setup/update.mjs --theme-done`. If it fails, or the same output has `extension installed: ink-themes`, do not run it: tell the person to quit and reopen Nimbalyst and run `/update-setup` again. With `extension waiting: ink-themes`, do not run it either: the Ink themes go in through step 10's card, and the person picks the look once Nimbalyst is open again (as below). Without the tool: Theme button at the bottom of the left bar, Ink themes, Ink Cobalt. A line `theme: set to Ink Cobalt` means it is written; Nimbalyst shows it once it is reopened. This happens once; a pick made afterwards stays.
8. **Nothing else.** An update changes files only. Open no project folder or window, and ask about nothing the first install covered (the look of the editor, dictation, the default model): the user has those as they want them. Ask only the questions in steps 2, 2b (the backup question among them, asked once while no answer is on record), 3 and 6, and the restart card of step 10.
9. **Reply**, short, in the language the user writes in (the chosen language after a language change):
   - the version it is on now and the `What is new` lines the script printed, except the one starting `What is new, for Claude:` (it asks you for the tour below; don't pass it on);
   - when the middle number of the version rose (26.4.4 to 26.5, not 26.5 to 26.5.1): offer a short tour and give it in the same reply, 3-5 lines from `~/.claude/setup-source/v<version>/docs/whats-new.md` (the installer unpacks each release there), in the person's language: how a job runs, the proof shown before "done", and two or three words from its table to try; then that path, so they can read the rest, and that "what's new" brings the tour back any time;
   - what the run listed at its end: the files it replaced, any retired skill it removed (one line each), any hook in the settings whose script is not there (name it, change nothing), and the file under `~/.claude/setup-logs` that has the whole run;
   - **the "Yours, on old versions" list**, whenever the run printed it: every file the user changed or had of their own, each with its `--replace` line exactly as printed (the same flag on `update.mjs` does the same, as in step 3). These stay behind this version until they take it; say so once, and that their own copy is kept either way. Say it even when they already answered the question in step 3 with "keep";
   - **start a new chat** for the next task: rules load when a chat starts. An installed extension shows the next time Nimbalyst starts; a waiting one goes through step 10;
   - anything that failed, with its output, and a `Backup:` line other than `Backup: not asked`, as it is;
   - one offer: in a project they work in, `/update-project` brings it up to this setup;
   - the `nimbalyst:` line of step 10, in one plain sentence.
10. **Nimbalyst, last.** The setup delivers Nimbalyst: the version it checked, with its fixes, and Nimbalyst's own updater off.
    - **The `nimbalyst:` line.** If it says `getting <version>`, run `node ~/.claude/scripts/nimbalyst-patch/deliver.mjs --wait`, then the same command with `--status`, and use that line instead. Any other line is only passed on (step 9).
    - **Waiting panels.** Then run `node ~/.claude/scripts/nimbalyst-patch/ext-swap.mjs --status`: `extensions: waiting: …` means panels are built (by this run or an earlier background one) and wait for Nimbalyst to close.
    - **The close path** is there when `staged.json` exists in `%LOCALAPPDATA%\ai-coding-setup\nimbalyst\` (Windows only; never on a Mac).
    - **The restart card.** When the `nimbalyst:` line says `restart to finish: …` or `<version> installs when Nimbalyst closes`, or panels wait, end after the reply with one question card (`AskUserQuestion`; in Nimbalyst `mcp__nimbalyst__AskUserQuestion`), options `Restart now` / `Later` (the last card below has `I'll quit it now` / `Later`). The card for each case:

    - `restart to finish` (the running Nimbalyst has no fixes yet, so it can't be closed for the update): `Restart Nimbalyst now to finish? After you pick Restart now, quit Nimbalyst once from its tray icon (right-click, Quit); the update and its fixes go in and it opens again in about a minute. Chats that are working right now stop, this one too.`
    - `installs when Nimbalyst closes`: `Restart Nimbalyst now to finish? It closes, the update and its fixes go in, and it opens again in about a minute. Chats that are working right now stop, this one too.`
    - only panels wait, with `staged.json`: `Restart Nimbalyst now so the new panels show? It closes, they go in, and it opens again in about a minute. Chats that are working right now stop, this one too. Later: they stay waiting and go in the next time Nimbalyst is quit.`
    - only panels wait, no `staged.json`: `Put the new panels in now? Quit Nimbalyst yourself within the next 2 minutes, and open it again once its window is gone; the panels go in between. After 2 minutes nothing changes. Chats that are working right now stop, this one too. Later: they stay waiting, and the next /update-setup offers this again.`

    What to do on each answer:
    - `Restart now` with `staged.json`: say in one line that Nimbalyst restarts now, then run `node ~/.claude/scripts/nimbalyst-patch/restart.mjs` as the very last call (it carries on by itself when this chat stops and puts waiting panels in too).
    - `I'll quit it now`, or `Restart now` without `staged.json`: run `node ~/.claude/scripts/nimbalyst-patch/ext-swap.mjs --after-quit` (it returns at once and waits up to 2 minutes for Nimbalyst to end, then swaps). Then tell the person in one line to quit Nimbalyst now (macOS: Cmd+Q; Windows: tray icon, right-click, Quit) and open it again once it has closed.
    - `Later`: one line, that it goes in the next time Nimbalyst is quit when `staged.json` exists, else (and for `restart to finish`) that the next `/update-setup` asks again.

    If the person wants Nimbalyst to update itself again: `node ~/.claude/scripts/nimbalyst-patch/deliver.mjs --off` (it puts the original app files back, at once if Nimbalyst is closed, otherwise when it next closes; `--on` undoes it).

Budget: about 10 tool calls.
