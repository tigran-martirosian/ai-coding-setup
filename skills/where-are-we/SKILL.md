# Where are we

The tracker is the record of a **job**: planned work over more than one session, kept as one `release` item named after the work (no kind word in the name), with one `task` item per plan row (a **step**), linked to the job by `collection`. A one-session fix gets no job. This skill reads it, writes only what a fact proves, and answers with the reading: how many steps are left, what runs, what waits for the user.

It runs when the user asks or `lead` calls it; nothing starts it on its own. Load the tracker tools first (ToolSearch `tracker_`). Trackers belong to one project, so this covers the open project only. Every `tracker_list` of steps passes `includeClosed: true`: by default it returns open items only, and a done step left out would be copied in again and drop out of the count.

**Words.** Statuses go to the user in plain words: to-do "To do", in-progress "Running" while a session works on it now and "To do, started, no session on it" when none does, in-review and waits-for-you "Needs you" (in-review is the user's read), done "Done", wont-do and duplicate "Dropped"; a job set to released is "Finished". A step's added fields: `step` (its short name from the plan), `stage`, `waitsOn`, `proof` (commit and session), `budget` (tool calls), `file` (the path of the file a step asks the user to read, review or check). When `tracker_list_types` shows the task type without the other fields or the waits-for-you status, the project lacks the task-type patch: give the reading from what exists, write nothing, and say `/update-project` adds the patch. When only `file` is missing, work as usual without setting `file`, and say `/update-project` adds it. Titles, bodies and comments follow tracker-texts.md next to this file: plain sentences a person reads without the plan; ids, hashes, row codes and file paths go in fields (step, proof, file) or linked files, never in the text.

**What it writes, and what it leaves to the user.** A status moves only on a fact (a commit on the plan's branch, a check that passed). A step whose result the user must see (a design, a screen, a text he reads, a look) goes to in-review at most: the user closes it, never this skill. It never deletes or archives an item, and never restarts or redoes a step, without the user's yes. Everything else it lists.

## Steps

1. **Find the job.** `tracker_list` with type `release`, the open ones (planned, in-progress). One open: take it. More than one: the one this session is linked to, else the one the user named, else the one with the newest activity (the newest `updated` of the job or any of its steps), as the tracker page orders them. None: offer, on one card, to make one named after the work of the newest plan file the user OK'd (a plan with job-list rows in `docs/`); make nothing without his yes. The job's description names its plan files (one job can have several, e.g. a design plan and a build plan); when it names none, ask for them once and write the answer into the description.
   Done when one job is chosen, or the user said no to a new one (then stop with that line).

2. **Copy new plan rows in.** For each row of each plan's job list with no step yet (when two plans use the same row name, the `step` carries the plan's short name, as `build T1`): match on `step` first, then `tracker_list` with `search` on the row's title as the duplicate check. Create the missing ones as `task` items: `collection` the job, `step`, `stage`, `budget`, status to-do, and `file` the path when the row asks the user to read, review or check a file; the title says the row's job in plain words, the body says what it is for and its Done when in plain words, and the plan file is linked (tracker_link_file); the Serves quote stays in the plan; stage is "<plan's short name> · <phase>" (tracker-texts.md, "From a plan row to a step"); `dependsOn` follows the plan's order. A row only the user can do (an OK, a look, a restart time) is a step too, owned by the user, status waits-for-you, `waitsOn` the step it waits for, `file` as above. No other step is made: work found mid-run goes into the running step's comment and the plan's notes, and becomes a step only after the user OKs it as a plan row. A row added after the user's OK of the plan (its `Changed <date>: <row>` line adds it) is copied only when that line holds the user's words for it (`user: "<quote>"`); otherwise it gets no step and is listed as "row without your OK". Before creating, run `node text-check.mjs --json` (next to this file) on the new titles and bodies and reword what it flags. A row whose Serves, Done when or budget changed in the plan gets its body and budget updated; its status, proof and comments stay. A row this session has claimed (its State cell holds this session's claim) is created or updated as in-progress with `linkSession: true`, so the step shows in this chat's Trackers section.
   Done when every plan row has exactly one step, or is listed as "row without your OK".

3. **Since last time.** Read the last grooming time from the job's newest comment starting `where-are-we: groomed` (no such comment: since the job was created). From each step's activity (`tracker_list` with `full: true`): what got done, started or parked (moved to waits-for-you) since then.

4. **Settle what facts prove.** A step in in-progress whose `proof` commit is on the branch the plan names (`git merge-base --is-ancestor <commit> <branch>`) and whose row's State cell reads `done <hash>` (written only after the row's Done when check passed): move it to done, or to in-review when its result is something the user must see. A commit alone proves nothing: without the `done` mark the step stays in progress. Add one comment in plain words (tracker-texts.md) saying what finished; the commit stays in proof. A step whose linked session finished without a commit: leave it as it is, list it.
   Done when every in-progress step is either moved on a fact or left with its reason.

5. **Stranded steps.** A step in progress for over a day (its last status change in activity) with no live session (its session from `proof` or the item's linked sessions, checked with the session tools): list it with its age and its last comment. A step in progress with no linked session at all: list it as "not linked"; the session that runs it links it with `tracker_update` and `linkSession: true`. Restart or redo none of them: the user decides.

6. **Ready gate.** A to-do step with no Done when in its body, or with an open question in its comments: list it as "not ready" with what it lacks. A not-ready step is not claimed until that is fixed. The open steps' titles and bodies go through `node text-check.mjs --json <temp file>` (next to this file) once, as one `{"name": <title>, "text": <title and body>}` per step: list each flagged step as "not plain" with the marks it found; above five, give the count and the first three. A flagged real name (a product, a file format, a quarter) or a link the user needs may stay. A not-plain step is reworded by tracker-texts.md only on the user's yes.

7. **What waits for the user.** Every in-review step (the user reads it and closes it), every waits-for-you step that can be done now, and every user step whose `waitsOn` step is done: one line each, the question in the user's words, with its `file` when set. A user step still waiting on other steps is named once as "later: after <step>".

8. **The reading.** Count the job's steps: dropped ones leave the total; left = total minus done; running = in-progress steps a session works on now (a live session, checked as in step 5), and an in-progress step with none is to do, "started, no session on it"; waits for you = step 7's lines (in-review counts here, never as running); calls left = the sum of `budget` over the steps not done ("up to"). Answer in one line first, as in "11 steps left of 27, 4 running, nothing waits for you, up to 210 calls left", then the lists of steps 2, 3, 5, 6 and 7, each left out when empty, and step 4's moves. Then add the comment `where-are-we: groomed <date and time>` to the job, followed by at most three plain sentences (tracker-texts.md) of what moved and what is left (no session ids, hashes or row codes).

9. **End of a job.** A job is finished when every step is done or dropped; a job with no steps yet is not finished and stays open. One whose `version` field is set ships as that version and also needs its git tag (`git tag --list`): without the tag it stays open, listed as "waits for its tag". A finished job is set to released with `releasedAt`, and `gitTag` when it has a version. When a version job's tag exists but steps are still open: ask on one card which of them the user keeps; the kept ones move to the next job (`collection` the open job the user names), the others become wont-do on that same answer, then the job is set to released.
